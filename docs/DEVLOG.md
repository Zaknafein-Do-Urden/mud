## 2026-10-16 项目启动

需求：网页端武侠 MUD；存档在本地，可导出文本文件跨浏览器导入；重剧情探索，未来文本量大；支持多人合作；部署在 GitHub Pages，没有任何后台服务器。

### D-001 本地存储用 localStorage 而非 cookie

**背景**：最初设想是"存在 cookie 里"，本意是"存档只在玩家本地，不在服务器"。

**候选**：
| 方案 | 容量 | 优点 | 缺点 |
|---|---|---|---|
| Cookie | 每条约 4KB | — | 容量太小（背包+剧情标记很快超）；每次请求都会发给服务器，浪费流量；可能被浏览器策略定期清除 |
| localStorage | 约 5MB | API 简单、同步、够用 | 同步 API 写大数据会卡顿（对我们的存档体量不是问题） |
| IndexedDB | 数百 MB | 容量大、异步 | API 繁琐，存档用不到这么大 |

**决定**：localStorage。完全满足"本地存档、服务器无数据"的本意。

**代价**：和 cookie 一样，用户清理浏览器数据会丢档；Safari 对长期未访问站点的存储有 7 天清除策略。→ 通过**醒目的导出按钮**和定期提醒导出来缓解。

**重新考虑**：存档超过 ~1MB，或需要存截图等二进制数据时，换 IndexedDB。

### D-002 localStorage 键名必须加前缀

**背景**：GitHub Pages 上同一用户的所有项目页（`用户名.github.io/项目A`、`/项目B`）属于**同一个 origin**，共享同一个 localStorage。

**决定**：所有键都以 `wuxia-mud:` 开头。

**代价**：无。

**附注**：若将来绑定自定义域名，origin 改变，旧存档读不到——迁移前必须提醒玩家先导出。

### D-003 原生 ES Module，无构建步骤

**候选**：
- **原生 JS + ES Module，不构建**：推到仓库即可上线；任何人改一行文本刷新即见效；没有工具链问题。缺点：没有类型检查，第三方库只能走 CDN（esm.sh 等）。
- **Vite + TypeScript**：类型安全，大项目更好维护，可打包内容。缺点：需要 GitHub Actions 构建部署，增加门槛。

**决定**：先不构建。早期最重要的是快速迭代玩法和内容格式。代码里用 JSDoc 注释标类型，必要时可让编辑器做检查。

**重新考虑**：代码超过 ~3000 行、或多人协作开发、或需要打包大量内容文件以减少请求数时，迁移到 Vite + TS（迁移成本低，ES Module 本来就是 Vite 的原生格式）。

**本地运行**：浏览器禁止 `file://` 下 fetch，需要起一个静态服务器：`python -m http.server 8000`。

### D-004 自定义 Markdown 风格内容格式

**背景**：剧情是重点，文本量会非常大。内容格式决定了写作效率。

**候选**：
| 方案 | 写作体验 | 分支剧情 | 其他 |
|---|---|---|---|
| JSON | 差（引号、转义、逗号） | 需自己设计 | 零解析成本 |
| YAML | 中（缩进敏感，长文本易错） | 需自己设计 | 需引入解析库 |
| Ink / Yarn Spinner | 好 | 非常强 | 为线性/分支叙事设计，与"房间-出口"的 MUD 空间模型不太契合；引入整套运行时 |
| 自定义纯文本格式 | 好（几乎就是写文章） | 够用 | 需要自己写解析器（约百行） |

**决定**：自定义格式（`=== 类型: id` 分块，行首 `?条件` 控制显隐，`* 选项 -> 目标 ?条件 !效果` 写对话）。具体语法见 DESIGN.md §5。

**理由**：MUD 的核心是"空间 + 状态"，而不是一条叙事流；自定义格式能直接表达房间/NPC/对话，写作者几乎不需要学。

**代价**：
- 需要自己维护解析器和语法文档。
- 没有现成的编辑器高亮/校验 → 计划写校验脚本跑在 CI 里。
- 所有剧情文本都在公开仓库里，**任何人都能直接看到全部剧透**。静态站点无法避免，混淆只是自欺；接受。

**重新考虑**：如果某段剧情需要非常复杂的分支叙事（大量变量、循环），可以考虑在那一类块中嵌入 Ink。

### D-005 不做存档防篡改

**背景**：存档是玩家自己导出的文本，玩家可以解码后修改。

**分析**：前端代码是公开的，任何"加密"的密钥也在代码里，只能挡住不懂技术的人。真正的防作弊需要服务器，而我们没有服务器。

**决定**：导出格式只做压缩 + base64 + 校验码。校验码的唯一目的是**发现复制粘贴时的损坏**并给出友好提示。

**影响联机**：联机时客户端带来的角色数据也无法验证。本游戏定位是朋友间合作，接受这一点（见 D-008）。

### D-006 回合制 + 指令时限的战斗（设计稿）

**候选**：
| 方案 | 优点 | 缺点 |
|---|---|---|
| 经典 MUD 实时心跳（每 1~2 秒自动出招） | 原汁原味，紧张感 | 文字刷屏，玩家来不及读；P2P 下需要持续同步，延迟和断线影响大 |
| ATB（各自读条） | 有节奏感 | 联机时读条同步复杂 |
| 纯回合制（轮流行动） | 简单 | 多人时等待其他人很无聊 |
| **同时选择回合制 + 时限** | 不怕延迟；有时间阅读；多人同时决策无等待；天然适合"合击" | 失去一些实时紧张感 |

**决定**：同时选择回合制 + 指令时限（默认 20 秒，单机可关闭时限）。

**武侠特色设计**：武功由招式组成；攻/守/闪三姿态克制；内力管理；**合击**作为多人合作的核心奖励——两人同回合使用可配合招式触发。战斗描述用经典 MUD 模板（`$N`、`$n`、`$招式`）生成，保证文本丰富又不需逐场手写。

### D-007 WebRTC + 公共中继信令（设计稿）

**背景**：没有服务器，浏览器之间要通信只能用 WebRTC。但 WebRTC 建立连接前需要"信令"交换连接信息，信令本身需要一个中间人。

**候选**：
| 方案 | 体验 | 可靠性 | 依赖 |
|---|---|---|---|
| 手动复制粘贴连接码 | 差（两人要来回粘贴两次） | 100%（只要网络能直连） | 无 |
| PeerJS 公共服务器 | 好 | 依赖他人维护的免费服务器 | 第三方 |
| **Trystero**（借助 Nostr / BitTorrent tracker / MQTT 公共中继） | 好，输入房间暗号即可 | 多个中继可互为备份 | 公共基础设施 |
| Firebase 等免费 BaaS | 好 | 高 | 实质上就是引入了后端，违反约束 |

**决定**：Trystero 为主，手动连接码为兜底。

**已知限制**：
- 没有 TURN 中继服务器时，约 10~20% 的网络组合（对称 NAT、公司/校园网）无法直连。不提供 TURN，允许玩家在设置里填自己的 TURN 地址。
- 公共中继可能偶尔不可用 → Trystero 支持多策略切换。

### D-008 主机权威 + "带角色入队"（设计稿）

**候选**：
- **完全对等 / 锁步（lockstep）**：每个人都跑一份引擎，只同步输入，要求所有计算完全确定（包括随机数和浮点）。带宽最小，但一处不同步就全盘错乱，调试困难。
- **主机权威**：房主跑引擎，其他人发命令、收结果。简单可靠。缺点：房主掉线则会话结束；房主可作弊。

**决定**：主机权威，星形拓扑。2~4 人规模下房主带宽不是问题；朋友合作不在意房主作弊。

**存档如何在联机中共存**：每个玩家的角色存档仍在自己浏览器里。入队时把角色快照发给房主，结束时房主把获得的经验、物品、**共同经历的剧情标记**发回各自写入存档。世界状态以房主的存档为准。

**未决问题**：
- 房主掉线后是否支持"房主迁移"？（初期不做，直接结束会话、各自保留已结算的收益）
- 剧情选择由谁做？（候选：房主决定 / 投票 / 触发者决定。待做到联机时讨论）

### 实现记录：第 1 阶段骨架

- 完成：房间移动、查看、NPC 对话（分支选项 + 条件 + 效果）、剧情标记、物品、自动存档、导出/导入（含损坏检测）、示例区域"临安城"。

## 2026-10-16 讨论：联机与战斗

结论来自用户对上一轮四个问题的回答。完整设计稿见 [MULTIPLAYER.md](MULTIPLAYER.md) 和 [COMBAT.md](COMBAT.md)。

### D-009 主线可联机，只有房主推进剧情

**背景**：玩家剧情进度不同时，联机听谁的。上一轮的候选：A 主线联机、B 联机只玩专门合作内容、C 混合。

**决定**：A 的一个受限版本。主线可以联机，但**只有房主的剧情会推进**。客人只出战力，拿战斗收益（潜能、银两、普通掉落），不获得剧情标记和剧情物品，也不影响自己的主线。

**理由**：
- 不需要单独写合作内容，所有主线内容天然都能联机，内容写作量不增加。
- 客人的存档只会"加东西"（潜能、物品），不会"改状态"（剧情标记），因此不存在两份世界状态合并的问题。

**代价**：
- 客人可能被剧透（看到了房主的主线剧情）。接受：是客人自己选择来帮忙的。
- 客人对剧情没有参与感，乐趣主要来自战斗和陪伴。所以战斗系统要足够有深度（见 D-012 ~ D-015），合击要有足够的回报。

**细节决定**：客人收益全额，不平分；掉落各自掷骰（个人掉落），避免分赃矛盾；标 `quest` 的掉落只给房主。

### D-010 客人强制跟随，只能建议

**决定**：客人不能独立移动，也不能做剧情选择。可以用 `建议` 命令向房主提议，房主可以一键 `采纳`。战斗中所有人平等，各自出招。

**放弃的方案**：投票（决定权分散，与"房主的主线"定位冲突）；自由行动（客人在房主世界里乱跑会触发房主的剧情）。

### D-011 旅店为联机入口与出口

**决定**：只能在旅店开设或加入队伍。队伍解散（含被踢、掉线）后，客人回到加入时所在的旅店。

**理由**：客人加入时的位置固定为旅店，所以"返回"等于回到原位，客人自己的世界从未被动过。这是让 D-009 成立的关键。旅店同时也是战败复活点（D-016），概念统一。

**待确认**：房主开队后可以带队离开旅店；解散时房主就地解散，不必回旅店。

### D-012 刚巧守克制倍率固定，与等级无关

**背景**：用户要求"武功练上去之后提升威力，但还是会被对应的武学克制"。

**候选**：
- 克制倍率随等级差变化：高手被克时损失小。→ 等级高了克制就无所谓，违背要求。
- **克制倍率固定**（暂定克 ×1.5，被克 ×0.5，相差 3 倍）。等级只影响攻击值。

**决定**：固定倍率。在威力相同时，等级要高出约 100 级（武功系数相差 3 倍）才能抵消克制。所以低手用对势可以和高手过招，但高手仍然更强。

**其他关键设定**：
- 守势**不直接攻击**，只对巧招化解并反震，可以护住队友（护法）。这让"守"有独特的玩法，而不只是"减伤"。
- 势是整回合的姿态，与攻击目标无关。
- 时序上巧招先于刚招结算，巧招打倒的人发不出刚招。

**待定**：倍率数值（×1.5 / ×0.5 还是更极端）需要实际打几场再定。

### D-013 内功为根基，所有招式耗内力

**决定**（用户要求）：内功等级提升气血、内力上限和全部武功的威力加成。所有招式都耗内力，包括守招。内力耗尽只能调息：空过一回合，恢复 10% 内力，调息时受到的伤害 ×1.2。

**衍生设计**：
- 外功等级上限 = 内功等级 + 20，逼玩家练内功。
- 吸内类武学（化功大法、吸星大法、北冥神功）和抗吸内武学（易筋经）。"抽干对手内力 → 对手被迫调息 → 队友集火"是一条完整的战术线，也给多人配合提供了理由。

**代价**：内力管理增加了一点操作负担。调息的 ×1.2 惩罚要小心，太大会让内力耗尽变成"必死"。

### D-014 无闪避、无未命中，随机性最小化（提议）

**理由**：用户要求"可研究"。如果命中靠掷骰，玩家很难判断一场战斗输赢是因为策略还是运气。去掉闪避和未命中，只保留 ±10% 的伤害浮动，战斗更像可推算的棋局。不确定性来自**对敌人意图的判断**（预兆、虚招），而不是骰子。

**代价**：少了"险险闪过"的戏剧性。可以用文字描述弥补：被克制时的"落空"本身就可以写成闪避。

### D-015 武学上限由剧情中获得的典籍决定（提议）

**理由**：把"探索剧情"和"武学成长"两个重点绑在一起。只学到上卷就最多 50 级，找到下卷才能继续练。玩家有动力探索，剧情作者也有了天然的奖励手段。

**代价**：典籍分布要和剧情进度精心配合。客人在别人的主线里看到了下卷的位置，但拿不到（剧情物品只给房主），只能自己回去打。这可能反而是好事。

### D-016 战败无惩罚

**决定**（用户要求）：战败后被人救起，回到最近的旅店，气血内力全满，没有任何损失。

**衍生**：剧情战可以指定 `onlose`，打输进入剧情分支（被擒、被救）而不是回旅店，让失败也成为叙事的一部分。

### 本轮仍待讨论（已在 D-017 中解决）

见 COMBAT.md 和 MULTIPLAYER.md 中的 ❓ 标记，主要有：
1. 克制倍率取值。
2. 战斗外内力是否自动回满。
3. 看破虚招的提示只给本人还是全队。
4. 是否显示伤害数字。
5. 战败是否仍给潜能。
6. 客人能否得到"偷学、顿悟"类收益。

### D-018 文字优先，但文字中的一切都可点击（提议）

**背景**：用户提出古早 MUD 受技术限制，只能输入命令、看文字流，现在网页技术能提供更好的体验。

**候选方向**：
| 方向 | 优点 | 缺点 |
|---|---|---|
| 保持纯命令行 | 最"正宗"，实现简单 | 门槛高，手机上几乎没法玩 |
| 图形化（地图行走、立绘、战斗动画） | 直观 | 美术成本巨大，和"大量文本"的定位冲突 |
| **文字为主 + 富交互** | 保留文字氛围；人名、物品、出口都可点；命令行保留给老玩家 | 需要在内容格式中加链接标记 |

**决定**：文字为主、富交互。正文中的人名、物品、出口可以点击，弹出动作菜单。命令行加上 Tab 补全和拼音首字母匹配。另外加入对话按钮、自动小地图、江湖笔记、PWA。详见 [UX.md](UX.md)。

**代价**：内容文件多了 `[[显示名|id]]` 标记。可以让解析器对已知的人名和物品自动加链接，减少手写。

### D-019 界面不提供文字之外的信息；队友出招实时可见（提议）

**原则**：界面只把文字里已有的信息整理得更好用，不额外"剧透"规则判断。例如战斗中**不**直接标出敌人这回合的势，否则读预兆的玩法就没了。

**例外**：队友已选的招式实时显示给其他队友。这不是对敌人信息的泄露，而是让合击配合成为可能。现实中并肩作战本来就能看到同伴的架势。

**相关**：合击提示只针对已经学会的合击，未知的合击要靠自己发现。

### D-020 视情况引入 Preact + htm（提议）

**背景**：战斗界面、侧栏状态、队伍栏、联机状态都要随时更新，纯手写 DOM 操作会越来越乱。

**候选**：
- 继续原生 JS：零依赖，但界面状态管理会变复杂。
- **Preact + htm**：约 4KB，可以从 CDN 以 ES Module 引入，**不需要构建步骤**，符合 D-003。
- React / Vue：需要构建，或者运行时体积大。

**决定**：先用原生 JS 做探索和对话界面。开始做战斗界面时，如果明显吃力，就引入 Preact + htm。引擎层（game.js）不受影响，因为它本来就不碰 DOM。

**决定**：不在内容里写坐标，从出口方向推算。冲突时自动错开，每个区域单独成图。

**代价**：迷宫类、非欧几何类地形（"往东走却回到了西边"）在地图上会显得别扭。真遇到时，可以给这类区域标 `map: none`，不画地图。这对迷宫本来就合理。

### D-022 链接颜色区分 + 悬停信息卡 + 右键固定

**决定**（用户提出）：
- 链接始终用不同颜色，与普通文字区分。
- 左键执行默认动作，悬停弹出信息卡，**右键固定信息卡**。
- 固定后可以继续悬停卡片里的链接，逐层查看，例如人物 → 门派 → 武功。

**补充设计**：最多固定 3 张卡；Esc 全部关闭；右键只在链接上拦截。手机端轻点相当于悬停，长按相当于固定。

**理由**：文本量大的世界里，玩家需要随时查"这人是谁、这门派是什么"。逐层固定的信息卡相当于一本随手可翻的江湖百科，又不会打断阅读。

**代价**：右键拦截与浏览器习惯冲突（比如"在新标签页打开"），但这些链接本来就不是网页链接，影响很小。

### D-023 逐段出现只用于重场戏

**决定**：只有标记过的段落（`scene` 块，或 `pace: slow`）才逐段出现，其余文字一次显示。

**理由**：节奏是一种强调手段，处处用就不是强调了，而且会拖慢日常探索。

### D-024 一书一主线，多主线并行于同一江湖

**决定**：
- 每部作品对应一条主线（`storyline`），主线下分章节（`chapter`）。
- 玩家是原创角色，亲历各部作品的事件，不扮演原著主角。否则多线并行时身份冲突，剧情也只能照搬。
- 命名空间隔离：一条主线只能写自己的标记（`<主线>.*`），可以读别的主线和 `world.*`。
- 共享地点由 world 定义，各主线用 `patch` 块往里追加条件文字、NPC、出口，不改写别人的内容。
- 人物归属唯一主线；共享物品归 world。
- 主线内容按需加载，避免文本量变大后首屏变慢。

**时代问题**（各书时代不同）：候选是 A 一个江湖不讲时间线、B 分时代多地图、C 一个江湖按时代分层。**提议 A**：地图可以复用，主线之间的交集最自然，有《金庸群侠传》的先例。待用户确认。

### D-026 trigger 块与 patch 块

**背景**：剧情需要"走进某个房间时发生某事"，比如进村时显示章节标题、受邀后进酒馆触发饮酒戏。主线还需要往共享世界里加东西，比如茶楼多一个选项、官道多一个出口。

**候选**：
- 在房间上加 `onenter` 属性：但触发逻辑属于主线，房间可能属于 world，这样 world 文件里就会混进主线逻辑。
- **独立的 `trigger` 块**：写在主线文件里，指定房间和条件。房间文件保持干净。

**决定**：
- `trigger`：属性有 `room`、`if`、`once`、`do`、`dialog`。`once` 的完成状态记为 `<trigger id>.done` 标记，自然落在主线的命名空间里。

**小规则**：patch 追加的对话选项插在"离开"类选项之前，保证"离开"总是最后一项。判断依据是选项既没有目标也没有效果。这有点隐式，已写进 DESIGN.md §5.1。

**代价**：首次使用需要下载几百 KB；依赖 CDN 可用性。做 PWA 时应把它加入离线缓存。

## 2026-10-16 补漏：物品无法使用

用户发现：竹哨拿到后不知道怎么吹，help 里也没有。原因是引擎根本没有"使用物品"的命令，剧情只用了 `has:` 条件。这是骨架阶段的遗漏。

### D-028 物品使用：use 命令 + use 块 + 物品专用动词

**决定**：
- 命令：`use 竹哨` / `使用 竹哨` / `用 竹哨`。
- **物品专用动词**：物品属性 `verb: 吹`，于是 `吹 竹哨` 也能用。背包里只有一件带这个动词的物品时，直接输入 `吹` 就行。武侠里"吹哨、点火、服药、读信"都比"使用"有味道得多。
- **use 块**：定义"在哪里、什么条件下用某物品会发生什么"。属性有 `item`、`room`（可省略，表示任何地方）、`if`、`once`、`do`、`dialog`。和 trigger 一样，写在主线文件里就属于主线，不会污染物品定义。
- 匹配顺序：指定了房间的 use 块优先于不限地点的；都不匹配时显示物品的 `usefail` 文字（没写就显示通用的"什么也没有发生"）。
- 界面：背包中物品的信息卡上出现"吹 / 使用"按钮；补全候选加入物品动词。

**放弃的方案**：把使用效果写在物品块里（`onuse:`）。同一件物品在不同主线、不同地点的效果不同，写在物品上会让物品块越来越臃肿，还会让 world 物品里混进主线逻辑。

**内容**：竹哨在西湖断桥吹响后，会出现一段雾中小船的短剧情，作为原创世界线索的引子。后续尚未编写。

**教训**：每加一种剧情手段（条件、效果），都要确认玩家有办法触发它。之后可以让校验脚本检查"有 `has:` 判断但没有任何 use 块的物品"。

## 2026-10-16 修复：剧情对话被打断后卡死

**用户报告**：进入曲三酒馆触发饮酒戏，出现两个选项时点击了"曲三"，进入和曲三的对话。结束后回不到原来的选项，剧情卡住。

**原因**：
1. 任何非数字命令都会结束当前对话，剧情对话也不例外。
2. 触发器设了 `once: true`，进门时就记为"已触发"。离开对话后，再进酒馆也不会重来。
3. 另一个同类隐患：当前对话只存在内存里。剧情进行到一半刷新页面，同样会卡死。

### D-029 锁定的剧情对话 + 对话状态存档

**决定**：
- 对话块可设 `lock: true`。锁定从这个节点开始，沿着选项一直延续到对话链结束，中间的节点不必逐个标记。
- 锁定期间只允许查看类命令（look、背包、help），执行完会重新列出选项。其他命令（包括点击人物、出口链接）一律提示"眼下顾不上别的"，并重新列出选项。
- 当前对话（id 和是否锁定）写入存档的 `dialog` 字段。读档或刷新后会重新显示该节点和选项，但不重复执行它的 `do` 效果（避免重复给物品）。
- 写作规则：**剧情关键的触发器不要只靠 `once`**，要以剧情进度标记为条件。例如饮酒戏改为 `if: flag:shediao.invited !flag:shediao.ch1_done`，即使出了意外，再进酒馆也能重来。这条同时救回了已经卡住的旧存档。

**放弃的方案**：
- 离开剧情对话后自动重新弹出：玩家会觉得被打断，而且还要决定什么时候弹出。
- 所有对话都锁定：日常闲聊（问路、打听）应该可以随时走开。

**后续**：校验脚本可以增加检查——由 trigger 或 use 进入、并且带选项的对话，提示作者考虑是否加 `lock`。

## 2026-10-16 开发：战斗系统第一版 + 门派

### D-030 门派系统：唯一门派、声望晋阶、三势齐备

**待定**：晋阶是否要考核、能否叛出师门、重复任务的限制、同门客人联机时的声望。都已在 SECT.md 中用 ❓ 标出，第一版采用最简单的做法。

### D-031 战斗实现中的数值调整

- **内力上限加了基数 50**：原公式（根骨×2 + 内功等级×系数）下，开局只有 40 点内力，打一招就得调息，开局战斗几乎全在调息。
- 敌人加 `hpx`（气血倍率）用来微调，泼皮 0.7。
- 同名敌人自动编号为"泼皮甲、泼皮乙"。否则预兆文字里分不清是谁。
- 平衡模拟结果（`tools/balance.mjs`，每项 200 场）：

| 战斗 | 角色 | 随机出招胜率 | 完美读招胜率 | 回合数 |
|---|---|---|---|---|
| 切磋小石头 | 开局 | 100% | 100% | 6~9 |
| 两个泼皮（入门任务） | 开局 | 38% | 100% | 8~9 |
| 地头蛇（二袋任务） | 开局 | 0% | 3% | 7~10 |
| 地头蛇（二袋任务） | 二袋 | 53% | 100% | 11~12 |

结论：**读预兆是胜负关键**，符合设计。问题：中等难度的战斗回合偏多（11~12 回合），可以再提高招式威力或降低敌人气血。等有更多武功和敌人后统一调整。

**理由**：
- 延续 D-029 的教训：任何"进行中"的状态都必须存档，否则刷新就会出问题。

### D-033 门派任务复用剧情机制，不做专门任务系统

**决定**：门派任务就是普通的对话 + 标记 + 战斗：领任务时设标记（让任务目标 NPC 出现），完成时在战斗胜利对话里清除标记并加声望。重复领取不受限制。

**理由**：写作者只需要学一套语法；剧情任务和门派任务可以自由混合。

**代价**：没有"任务日志"界面，玩家可能忘记领了什么任务。等做江湖笔记（UX.md §3.4）时一起解决。

## 2026-10-16 讨论：成长体系修正 + 地图 + 射雕第二章

### D-035 实战经验；门派武功从 1 级学起；内功气血内力永久累加

**背景**：上一轮我把门派武功改成从 10 级学起，理由是"学了反而比基础武功弱"。用户指出这正是想要的设计：

> 战斗时可以选用 1 级的门派武功还是 10 级的基础武功，用哪门武功就长哪门的经验。所以有取舍：牺牲眼前的战斗力去长门派武功的经验，还是先用基础武功打赢再说。

**决定**（推翻 D-030 中"从 10 级学起"）：
- 门派武功从 **1 级**学起。
- 新增**实战经验**：战斗中每用一次某门武功的招式，这门武功获得 `10 × clamp(对手水平 / 武功等级, 0.2, 3)` 点经验。升级需要 `(等级+1) × 20` 点。内功、轻功按运功回合数获得经验。对手水平取敌人武功等级的平均值。
- **内功增加的气血、内力永久累加**：所有已学内功都算，与当前装备哪门无关。当前装备的内功决定威力加成、护体、亲和与特性。这也顺带解决了上一轮"换内功导致气血骤降"的问题，所以不再需要"自动装备内功不降级"作为补救。不过保留它，因为威力加成仍然取决于当前内功。
- 外功上限改为"已学内功的**最高**等级 + 20"，换内功不会让上限变化。
- 胜负都给经验（练了就是练了），潜能仍只在胜利时给（D-017）。

**测试**：用 1 级莲花掌打小石头一场，升到 3 级；用 10 级基础武功打同一个对手，经验只有 1 级武功的五分之一左右。取舍成立。

**我的教训**：看到"新学的东西更弱"，先想一想这是不是有意的设计，再动手"修复"。

### D-036 晋阶考核：与照搬自身功夫的同门过招

**用户要求**：晋阶要考核，打一个势均力敌的对手。

**候选**：
- 为每个阶位手写一个考核对手：数值难以和玩家的实际成长匹配，太强或太弱。
- **镜像对手**：照搬玩家当前的属性、武功、等级和装备。

**决定**：镜像对手。永远势均力敌，而且考的是玩家读招的能力，而不是数值。对手名字由门派的 `examiner` 属性指定（丐帮：黎生）。考核前气血回满；输了无惩罚，随时可以再来；允许认输。

**代价**：镜像对手的出招没有门派风格（各势权重相同）。之后可以给考核者加上该门派的出招偏好。

### D-037 可以叛出师门：本门武功减半并冻结

**用户决定**：可以叛出师门，但门派武功等级减半，且不能再提升。

**实现**：`叛出师门` 只显示后果，`叛出师门 确定` 才执行。本门武功等级减半（至少 1 级），记入 `frozen`，上限锁定为当前等级，修炼和实战经验都无效。叛出的门派记入 `formerSects`，不能再回去（我的补充）。存档升到 v4。

**门派任务**：用户确认不限制重复次数。

### D-034 结论：区域地图

**用户决定**：常驻右侧，可以收起。

**实现**：SVG 自动布局（`src/ui/map.js`）。
- 以区域内第一个房间为原点做广度优先，按出口方向放格子，冲突时螺旋找空格。原点固定，所以走动时地图不会跳。
- 显示去过的房间，以及与之相邻但没去过的房间（虚线"？"）。跨区域出口画成边缘的短线，标注目的地名。
- 点击去过的房间会**自动寻路**，遇到对话、战斗、重场戏时停下。
- 宽屏常驻右侧，窄屏默认收起，用状态栏的"地图"按钮切换。展开状态记在 localStorage（属于个人偏好，D-001 允许）。

### D-038 射雕第二章：打赢打输剧情都继续

**内容**：第二章「火照牛家村」。官兵夜袭，郭啸天遇害，杨铁心负伤失踪；玩家在江边追上带队的军官段天德，李萍被他挟持上船北去；一位衣衫一尘不染的白衣公子"恰好"救下了包惜弱。玩家得到段天德的腰牌。
- 分支：正面冲过去，或者从侧面绕过去。绕过去的玩家会看到一个披斗篷的人在给军官出主意，结尾会觉得白衣公子和他身形相像（为日后的剧情埋线索）。
- 两场战斗（官兵、段天德）都写了 `lose` 分支，并设 `flee: false`。打赢打输剧情都会继续，只是文字不同；打赢段天德会记下 `shediao.beat_duan`。

**设计取舍**：原著的结局（郭啸天死、李萍被掳）不能被玩家改变，否则后面的主线就无从展开。所以让玩家的战斗**影响过程和细节，不影响结局**：赢了是"眼睁睁看他挟持人质逃走"，输了是"醒来时船已离岸"。这也符合"失败无惩罚"（D-016）：输了不会卡关。

**平衡**：段天德对开局角色几乎打不过（完美读招胜率约 2%），对丐帮二袋角色可以赢。这是有意的：这一战打输本身就是剧情。

**注意**：剧情台词避免对玩家使用有性别的称呼（"兄台""野小子"已改为"这位朋友"等），因为玩家角色的性别没有设定。

### D-039 内容文件不使用浏览器缓存

**发现**：测试第二章时，浏览器用了缓存里的旧 `ch01.md`，导致夜袭后郭啸天、杨铁心仍然站在院子里。

**决定**：读取 `index.json` 和内容文件时使用 `cache: 'no-cache'`：每次都向服务器确认，没有变化时服务器返回 304，几乎没有额外流量。

**遗留**：JS 模块本身仍可能被缓存。GitHub Pages 的缓存时间是 10 分钟，部署后最多 10 分钟就会更新，暂时接受。如果以后出问题，再给入口脚本加版本号。

### D-040 城市、马车、跑商、劫道、钱庄、城市差事

详见 [ECONOMY.md](ECONOMY.md)。

**结构**：
- 6 座城市：临安、嘉兴、襄阳、洛阳、长安、成都。每座城六个地点：十字街、车马行、市集、钱庄、客栈、衙门。门派驻地挂在城外，用 city 的 `areas` 归属到城市。
- 5 座新城市的骨架由 `tools/gen_cities.py` 生成，每座城手写一份描述、货物、路线、本地匪患。生成的是普通内容文件，可以手改。

**马车的实现**：复用对话的选项机制。车马行 `乘车` 生成一组临时选项，每个选项带 `travel:城市` 效果。大地图点击城市就是发送 `乘车 城市`。没有专门的旅行界面，但可以点击、可以用数字键选，和对话的操作一致。

**数值**（待平衡）：
- 被劫概率 `min(65%, 3% × 天数 + 50% × 货值 / (货值 + 2000))`。

**面板**：人物（状态 / 武功 / 天赋 / 背包）、江湖（主线 / 任务）、市集、钱庄。详见 UX.md §8.7。

**命令对照**（都有按钮了）：状态、武功、装备/卸下、修炼、学、晋阶、叛出师门、天赋、背包/使用、行情/买/卖、存/取、乘车（大地图）、休息（情境按钮）。仍只有命令的：look 某物（可以用悬停信息卡代替）、导出导入（顶栏按钮）。

### D-048 联机第一版

按 MULTIPLAYER.md 的设计实现（实现细节见该文档 §9）。

**传输层**：Trystero 0.21.5（Nostr 信令），从 esm.sh 按需加载。另做了一个 BroadcastChannel 实现，接口完全相同，用 `?net=local` 切换。它有两个用途：开发时在同一浏览器的两个标签页里测试，不依赖外网；玩家在一台电脑上开两个窗口体验。测试时两种都跑通了。

**最重要的设计：输出按接收者分发**
- 引擎输出条目加 `to` 字段，没有就是广播。这样"只给看破者的提示"（D-017）、"建议只给房主"、"客人自己 look 的结果只给他"都只是同一个机制。
- 房主执行的私事命令不广播（看状态、买卖、存钱等）。

**组队战斗的视角问题**：单人时战斗文字里玩家叫"你"。组队时如果还用"你"，大家都分不清谁是谁。
- 候选：A. 每人一份引擎输出（复杂，等于每回合结算多次）；B. 统一用真名，发给每个人时把他自己的名字替换成"你"。
- 选了 B。只替换战斗类的输出（预兆、出招、伤害等），不碰剧情对话（以免把 NPC 台词里叫玩家名字的地方也换掉）。
- 代价：如果玩家名字和敌人名字有重叠就会误替换，概率很小，暂时接受。

**组队出招**：
- 每个玩家单位带 `pid`。所有站着的玩家都出招后才结算。
- 每回合 20 秒，超时自动调息。计时器在房主的界面里，引擎只提供 `combatTimeout()`，保持纯逻辑。
- 队友出招实时广播（D-019）。只有房主能下令撤退。
- 敌人气血 × (1 + 0.7 × (人数 - 1))。

**客人的命令分三类**：
1. 本地执行：状态、武功、天赋、装备、背包、帮助。调整装备、天赋后自动把新快照发给房主。
2. 发给房主：战斗出招、看、说、建议。
3. 其余一律自动变成"建议"：走动、交谈、对话选项、使用物品……这样客人可以照常点击一切，房主决定是否采纳。

**结算**：房主用客人的快照算出各武功的经验量，发 `settle {seq, exp, potential, hp}`。客人用同一套 `gainExp` 公式作用在自己的存档上，结果与房主那边的快照一致（测试验证过）。序号去重，防止重发导致重复入账。

**客人的地图**：显示房主所在的位置。房主发来该区域自己去过的房间，客人的存档里不记录这些地方（D-009：不影响客人自己的世界）。

**其他**：
- `?slot=2` 使用另一个存档位。同一浏览器的两个标签页共享 localStorage，没有它就没法在一台电脑上测试联机。
- 内容指纹（index.json 的哈希）不一致时拒绝加入。
- 客人入队后加载所有主线内容，否则房主剧情里的链接在客人那边显示不出来。

**测试中发现并修复**：客人发来的命令，房主只做了分发，自己那份没有显示，导致建议看不到。已改为分发后同时显示。

**未做**：合击（COMBAT.md §8）、房主掉线后的房主迁移、TURN 中继、手动复制连接码的兜底方案（D-007 中提到）。

### D-051 难度标准：猜对 80%

**模拟玩家**：每回合以给定概率选中克制的势，否则选另外两势之一（模拟器知道敌人的真实意图，所以"猜对率"就是玩家实际选对的比例）。

**主线必胜战：自适应气血**
- 开打时先把敌人伤害设为 0.45 倍，再二分查找敌人气血，使猜对 80% 的玩家胜率约 65%。整个过程模拟约 400 场，在浏览器里只要一瞬间。
- **为什么要先降伤害**：只调气血时胜率曲线太平：猜对 70% 也能赢 45%，达不到"以下会输"。战斗太短，运气成分大。降低敌人伤害、相应增加气血后，战斗变长，胜负更取决于猜对率：90% → 96~99%，80% → 71~80%，70% → 26~45%。
- 因为每次开打都重新计算，玩家练强了再来，敌人也相应变强，门槛始终是"猜对 80%"。这满足了"不管功力如何"的要求。代价是这类战斗没有"练级碾压"的爽感，但只用于主线必胜战。

**固定难度的战斗**（门派任务、城市差事、陪练除外）：新增 `tools/tune.mjs`，为每场战斗指定面向的玩家阶段（开局、入门、二袋），找出使该阶段猜对 80% 时胜率约 75% 的气血倍率，写进战斗块的 `hpx`（新增的战斗级倍率；同一个敌人可以出现在难度不同的战斗里）。
- 第一次调校时，新增的门派三阶任务和高阶城市的飞贼需要 4~8 倍气血才达标。这意味着敌人"打不疼人"，战斗会拖得很长很无聊。所以改为提高它们的武功等级（攻防一起提高），一阶新任务改为两个对手，再调校。最终倍率都在 1.0~2.4 之间。

**平衡工具**改为按猜对率（60%~100%）列出胜率，取代原来的"随机 / 完美读招"两种打法。

- 房主开队后同时待在两个房间：自己的队伍房间（随机长串，玩家看不到）和大厅。在大厅里每 3 秒广播一次队伍信息：房主名、人数、上限、协议版本、内容指纹。
- 客人点"搜索队伍"进入大厅，并发一个 `search` 请求，房主收到后立刻广播，所以列表几乎马上就有内容。之后随广播实时刷新。10 秒没有消息的队伍视为已解散；房主解散时会发 `gone`。
- 客人点"加入"后离开大厅，连接该队伍的房间。之后流程和原来一样。

**候选与取舍**：
- 继续用暗号：最简单，但要通过聊天软件传暗号，体验差，用户明确不要。
- 公共中继上的"房间列表"服务：Nostr 本身可以发布查询事件，但要直接对接协议，复杂度高。
- **大厅广播**（采用）：复用现有传输层，几十行代码。代价是房主要多维持一个连接，大厅里每个房主每 3 秒一条小消息。玩家多了以后流量会增加，届时可以改为"只在有人搜索时才广播"（已经有 `search` 请求，改起来容易）。

**版本不一致**：列表里照样显示，但标注"游戏版本不同"，不能加入。这样玩家知道朋友在，只是需要刷新页面。

**踢人**：房主的队伍栏每个成员后面有"踢出"按钮（会二次确认），也可以输入 `踢出 名字`。被踢的客人收到"你被××请出了队伍"，回到自己加入时的旅店，与主动离队相同。

**测试**：
- 本地通道三个标签页：两个房主同时开队，第三人搜到两个队伍；加入后列表人数变为 2/4；一个房主解散后从列表消失；踢人后客人回到旅店。
- 真实网络（Trystero）：搜到队伍并加入成功。房主同时连着大厅和队伍两个房间，没有问题。

### D-068 武学威力与战斗力：剧情武学按进度授予

**用户要求**：过射雕及后续剧情时传授相关的武功秘籍；建一个公式平衡武学威力和获得的时间——必须能打过战斗力 100 的敌人，才能获得威力大于 100 的武学，避免早期就拿到最终的强力武学。建文档管理。

**决定**（详见 docs/POWER.md）：
- 一把尺子量两边：**攻击值** = 招式威力 × (1 + 等级 × 2%) × 内功加成，就是伤害公式里出手的那一部分。
  - 武学威力 WP：练到某等级时最强一招的攻击值（内功加成按 1，带控制效果的招式 +10%/个）。内功、轻功没有招式，按威力 25 的"标准招式"折算。
  - 敌人战斗力 CP：它最强一门外功在它等级下的 WP × 它的内功加成。
- 规则：剧情授予（`learn:`、`cap:`）后的威力 ≤ 本主线到这一章为止必须打赢的最强战斗力。允许打输的剧情战不计入。门派武学和武馆武功不受此规则约束（各有自己的成长线）。
- 公式放在 `src/power.js`；`node tools/power.mjs` 打印报表；`validate` 违反规则时报错。

**为什么用攻击值，而不是"武功等级"之类**：等级相同的两门武学强弱差很多（降龙十八掌 10 级就有 79，小巧掌 10 级只有 17）。攻击值直接就是伤害公式的一部分，两边可以比较，也好解释："你拿到的武学，满上限时出手和你打赢过的最强敌人一样重"。

**按规则检查现有内容，超标的调整**：
- 内功、轻功的标准招式起初取威力 30，偏高（10 级就 36），改为 25（门派入门招式的水平）。
- 飞燕身法：第一章原给上限 30（威力 40，而第一章只打过战斗力 31 的刺客），改为只给 10 级，30 并入第二章（直接到 60）。第四章给上限 100（威力 75），而铁算盘只有 61；铁算盘是竹哨线的终局头目，对质门槛又要求外功 45 级，所以把他调强到 76（武功 40~44 级）。平衡工具复核：猜对 80% 胜率 60%~74%。
- 重阳宫信物：第一章就拿到，以前随时能换上限 60 的全真心法（威力 55，第一章还没打过任何必胜战）。改为第四章之后才能用；之前去，马钰会婉言请你先帮丘处机把事办出眉目。第五章开头本来就要回重阳宫，正好在那时用。信物支线在 `index.json` 里也挪到第四章之后，让检查的顺序和实际一致。

**决定**：
- 倍率表里列出的 = 本地有的货：能买能卖，价格照旧。
- 没列出的 = 本地没有的货：显示价格，不能买；能卖，按基准价（`UNLISTED_MULT = 1.0`）× 当日波动收购，同样打九折。
- 为什么按基准价：本地没有这种货，说明既不产也不常有人运来，按"市面上的一般价格"收是最自然的。它比运到缺货的城市（倍率 1.2~1.5）便宜，所以不会冲掉跑商的意义；在买价高于基准价的地方进货、拿到这种城市去卖会亏本，没有套利空间。
- 市集面板：本地没有的货在"买入"一栏显示"本地无货"，买的按钮不能点；本地有的货排在前面。命令行 `行情` 同样标出"本地无货"，`买` 本地没有的货会说明原因。

### D-077 跑商：特产便宜、外地货贵；马车 100 件

**用户要求**：本地产出的商品要便宜，本地没有的要贵。跑商的核心就是收购本地特产，运到没有这种物产的外地卖，再收购当地特产运回来卖。价格可以有随机变化，但大方针不变；跑商唯一的风险来自路上的劫匪。马车容量扩大到 100。

**原来的问题**：每座城的倍率表把大部分货都列上了，倍率 0.75~1.5 混在一起，有的城既卖某货也收某货；D-076 又让没列出的货按基准价收。结果"特产便宜、外地货贵"并不成立，有的路线还会亏。

**决定**（ECONOMY.md §3）：
- 城市 `goods` 只列**特产**，倍率 0.6~0.7，只有特产能买。每座城 2~3 样，按原来的设定分配（临安丝绸茶叶、嘉兴丝绸盐、襄阳铁器药材、洛阳瓷器铁器、长安皮货盐、成都蜀锦药材茶叶）。
- **外地货**的倍率 = 1.15 + 0.06 × 离最近产地的路程（天），封顶 1.8。用路程而不是固定倍率，是为了让"跑得越远赚得越多"成为自然的结果，和劫道概率随路程增长对应起来：利润和风险一起涨。路程用车马行的路线算最短路（`travelDays`）。
- 每日波动从 ±15% 收窄到 ±10%：保证波动再差，特产运到最近的外地也赚钱。
- 马车 100 件。劫道概率里的货值尺度从 2000 调到 5000：满载的货值是原来的五倍，不调的话几乎每趟都被劫。现在满载时 4 天路程约 37%，8 天约 49%，15 天封顶 65%。
- 市集里特产标"（特产）"，外地货标"本地无货"；"买5"改成"买10"。行情下面加一句说明规则。
- 校验：城市 `goods` 倍率必须 ≤ 0.8；每种货至少有一个产地。`tools/gen_cities.py` 里的数据同步更新。
- D-076 里"未列出的货按基准价收"作废，改为上面的外地货价格。

**验证**：脚本穷举 55 条"特产 → 不产它的城市"的商路，每条按 100 天的实际行情算：全部赚钱，最差的一天 +33%（长安的盐运到临安：临安离嘉兴的盐产地只有一天路，所以盐在临安不算贵）；远途平均 +170% 左右；临安、嘉兴之间一天路程也有 +43%~+69%。游戏里在襄阳实测：铁器、药材标为特产，其余标本地无货，满载 97 件铁器，带来的蜀锦卖出高价。

**决定**：把家丁的刀法压到 18 级以下，钟万仇改用自己的「断魂刀法」（没有群攻招），曲线回到 36 → 58 → 73 → 88，正合 TIANLONG.md 里"段誉线结束约 90"的建议。四章授予的武学全部通过 `node tools/power.mjs` 的检查。

### D-209 后段敌人的虚招、藏招比例要压低（天龙）

**现象**：云中鹤（虚招 35、藏招 25）在 `balance.mjs` 里"猜对 100%"只有 73%~75% 的胜率，"猜对 80%"掉到 52%，低于 D-051 的 60%~80%。

**原因**：藏招的回合不给预兆，玩家读得再准也只能瞎猜，等于给胜率加了一个天花板；虚招同理。敌人越到后面越爱配这两项，结果把"按猜对率吃饭"的难度标准顶坏了。

**决定**：必胜战里的强敌，藏招压到 10% 上下、虚招 20% 上下（云中鹤 12/22，吐蕃武士头领 10/20，吐蕃武士 5/15，恶人谷爪牙 5/18）；必败战（南海鳄神、鸠摩智）不受此限，照旧配得很高——那两场本来就不指望看破。

调完之后的"猜对 80%"一栏：恶人谷爪牙 71/73/71，云中鹤 62/66/65，吐蕃武士 55/60/76，武士头领 64/66/57。**两个以上敌人的战斗会低一些**（猜对率只针对其中一个敌人，D-051 原文已说明曲线更平缓）：作为对照，已经上线的射雕第五章侍卫统领一战是 60/51/68。另外吐蕃武士原本配到刀法 25 级（解锁带内伤的「断岭」），两个一起上对低功力角色太狠，压到 22 级。

### D-211 换房间的 `goto:` 要放在"没有选项的过场对话"里（天龙）

- 写成**选项的效果**（`* …… !goto:x`）：`choose()` 先 `apply(effects)`（新房间的触发把下一段对话打开），接着因为这个选项没有 target 就 `endDialog()`，把刚打开的那段对话关掉了（`src/game.js`）。

### D-214 北冥神功吸内力：内功的 `absorb`，战斗中可临时超上限（天龙）

**用户要求**（2026-10-17）：北冥神功要能够吸内力，不过只加战斗时的内力，可以临时突破上限，战斗后上限不变。取代 D-205 里"回避新机制"的做法。

**实现**（`src/combat.js`，约 10 行）：内功可以写 `absorb: 比例`。装备这门内功的人每一次**没被克制**的攻击，都会把对手 `伤害 × absorb` 的内力吸过来（对手有多少吸多少）：
- 吸来的内力**故意不夹 `maxMp`**，可以超过上限；
- 内力本来就不进存档（每场战斗开打时按上限重置，`playerUnit`），战斗一结束自然回到原样，所以"战后上限不变"不需要额外代码；
- 顺手修了两个本来就有、现在才会碰到的小毛病：内力高过上限时，调息和「回气」的 `Math.min(maxMp - mp, …)` 会算出负数，反而扣内力，加了 `Math.max(0, …)`。

**数值**：北冥神功 `absorb: 0.4`。实测 40 级北冥、打点苍马贼，六个回合从 650/650 吸到 679/650，对手内力掉了七成——既是补给，也是压制（对手内力见底就会"招式使到一半便泄了气"）。

**威力折算**（`src/power.js`）：带 `absorb` 的内功按 +5% 计，和招式效果「吸内」同一个系数。北冥上限 60 的威力从 55 变成 58，仍然低于第四章的 88。`tools/validate.mjs` 增加检查：`absorb` 只能写在内功上，取值 0~1。

**一个要留意的副作用**：必胜战的自动调整（D-051）按玩家的武功等级估功力，没把"吸内"算进去，所以装着北冥神功打剧情战会比 65% 的目标稍微轻松一点。目前只有一门内功有 absorb，先不为它改自适应算法。

**剧情跟着改**：第二章段誉改成"整卷都抄给你"——他自己决不练后半篇，但那是他的选择，不替你决定。第一章他的"我不练"保留。

### D-312 两处"同一个房间里连着两段剧情"的坑（笑傲）

写第三章时踩到两次 D-210／D-211 那类问题，记下来给后面的人：

### D-222 平衡脚本加第四种角色"后期"；以及"三个以上的强敌"会把自适应顶到底（天龙）

**现象**：第八 ~ 十章的以少敌多，用 `balance.mjs` 一跑，低功力角色的曲线整个是塌的——谭公谭婆加赵钱孙三个一起上时，"开局"角色**猜对 100% 也只有 50% 胜率**，自适应气血已经压到 ×0.10（底）。

**原因**：自适应（D-051）只调敌人的**气血**，不调他们的**输出**。敌人一多，每回合挨的伤害是叠加的，气血再怎么压也救不回来——这时候胜负不再取决于"猜得对不对"，难度标准就失效了。

**两条处置**：
1. **战力一百五以上的剧情战，同场敌人压到两个**（头目＋一个小兵），最多三个小兵。第八章的三打一改成"徐长老拦下谭公"，第九章进院的黑衣人从三个改成两个，第十章厅上第一波从四个改成三个。改完"猜对 100%"回到 80% ~ 100%。
2. **`tools/balance.mjs` 增加第四种角色"后期"**：门派武功四阶上下（60 级）、内功 60、带轻功。前三种（开局／入门／二袋）量的是前期剧情，后段章节本来就不是那种功力的人能走到的——第六章的门槛就要巧 50 或内功 45。加了这一档之后，第八 ~ 十章六场战斗在"猜对 80%"一栏是 67 / 71 / 59 / 70 / 64 / 70，正落在 D-051 的区间里。

### D-227 平衡报表为什么老是差几个百分点：自适应气血只用 40 次模拟拟合（天龙）

写第二十一章时又撞上 D-226 里那条"陡峭战斗估不准"的说法，这一回查到了底，**结论要改**：

- `balance.mjs` 的随机种子是固定的（12345），所以同一场战斗跑多少次，结果**一模一样**。那就不是运气，是系统性偏差。
- `adaptEnemyHp` 用二分法找气血倍率，每一步只模拟 **40 次**来估胜率。40 次的抽样误差约 ±8%，二分法等于拿这 40 次的结果**过拟合**：它找到的是"在这 40 局里恰好 65%"的那个倍率，真实胜率可能落在 57% ~ 73%，偶尔更偏。
- 所以**调敌人等级是白费力气**（这一条 D-226 说对了），但原因不是战斗陡峭，而是自适应会把气血顶回到同一个过拟合点上。去掉摩云幡的"化内"效果之后报表一个数字都没变，就是证据。

**处理**：`tools/balance.mjs` 里把自适应的样本数提到 120（`adaptEnemyHp(db, b, { n: 120 })`，再高就太慢了）。摩云子那一场的"猜对 80%"立刻从 52% 回到 68%；第十七章星宿派那一场（D-226 里压在 59% 的那个）也从 51% 回到 64%——**那些低数字从来不是设计值，是量错了**。报表慢了两三倍，但一章只跑一次，值。

**引擎里的 40 不改**：玩家每次开打的种子是随机的，等于每场仗在 65% 上下浮动 ±8%，这点浮动反而是好事（同一场仗，有人觉得险，有人觉得顺）。真要改，代价是每场剧情战开打前多算一秒，不划算。

**给后来人**：报表上出现 50% 出头又怎么调都不动的数字，先怀疑是量法，别急着改内容。

### D-100 多个敌人时，默认目标保持在上回合攻击的那个

**用户报告**：战斗中有多个敌人，前一回合选了攻击第二个敌人，到下一回合默认又回到第一个。

**原因**：两处。①引擎记"上次打的对手"（`lastTarget`）时，守招也会记，而守招的目标是自己或队友；中间出一次守招，下回合面板就找不到这个目标，退回第一个敌人。②战斗面板每次刷新都重画，玩家点选敌人只记在那一次渲染里，没出攻招之前刷新一次（下一回合、组队时队友出招）就丢了。

**决定**：①只有攻招才更新 `lastTarget`。②面板外记住玩家最后点选的敌人，刷新后照样选中它；换了一场新战斗（回合数变小，或敌人名单不同）才清掉。默认目标的顺序：最后点选的 → 上回合攻击的 → 第一个活着的。

### D-101 剧情暂停时，别的操作都无效

**用户要求**：剧情逐段显示、停在"点击或按空格继续"时，应该限制其他操作，点别的按钮都无效。

**原因**：以前任何命令进来，都先把剩下的剧情一口气倒完（`flush`）再执行，所以点别的按钮等于跳过剧情。

**决定**：
- 剧情暂停时 `run()` 不接受新命令；继续的方式只有：点文字区、按空格、输入框为空时回车。
- 页面加 `pacing` 状态：顶栏、快捷按钮、地图、战斗面板、队伍栏变暗且点不到。
- 文字区里的链接这时点了只算"继续"，不触发链接本身（捕获阶段拦下）。
- 输入框里打了字再回车，也只算"继续"，打的字留着，剧情走完再发。
- 点了别处时，"点击或按空格继续"闪一下，提示该点哪里。

**验证**：浏览器里在断桥吹竹哨（逐段显示的剧情），暂停时用真实点击试了人物按钮、地图上的房间、快捷按钮，都没反应；点正文里的出口链接只往下走一句、没有走动；剧情走完后一切恢复。

### D-102 自适应气血封顶 3 倍，不够再加强敌人伤害

**用户报告**：射雕第二章打两个官兵，每人 1400 多点血，太难了。

**原因**：必胜的剧情战按玩家当前实力自适应（先把敌人伤害降到 0.45，再二分查找气血倍数，让 80% 猜对率下胜率约 65%）。倍数上限是 20。玩家比官兵强很多时，官兵太弱、降了伤害打不动玩家，只能靠堆气血拖长战斗，于是变成十几倍血的肉盾，打起来又长又闷。

**决定**：
- 气血倍数上限改成 3（`ADAPT_HP_CAP`）。气血放到 3 倍还是太容易时，气血停在 3 倍，改为二分查找敌人的伤害倍数（0.45 ~ 8）。效果：弱敌打得快，但每一下都疼，胜负仍然取决于猜对率。
- 平衡结果（`shediao.b.soldiers`，猜对 80%）：开局 66%、入门 67%、二袋 68%；后期角色 97%（伤害放到 8 倍也打不动，ch2 的官兵本来就该被后期角色碾过去）。
- 弱敌打得快了，战斗时长更合理；强敌（气血不到 3 倍就平衡的）不受影响。
- 实测开局角色打这一战：官兵原血 136，旧算法放大到 9.4 倍（1278 血），现在 408 血、伤害 ×1.22。自适应的计算也从约 23 秒降到约 9 秒（node 里测，敌人血少了，模拟的战斗更短）。9 秒仍然偏长，以后可以考虑减少模拟次数或缓存结果。

### D-106 自适应改为按"三势最狠的招 + 气血"直接计算；必胜战变容易

**用户要求**：判断玩家强度不该看功法等级之和（修为），因为学了多个功法，最后主要用的也就刚、巧、守各一个。应该看最厉害的刚、巧、守功法能造成多少伤害，再结合气血算出强度，用它动态计算敌人强度。现在实践中敌人太强了。

**先说明**：自适应以前其实不看修为，而是拿玩家的真实武功模拟几百场战斗，找"猜对 80% 胜率 65%"的敌人气血（D-051）。问题是：①标准太高，真人很难猜对八成；②模拟要好几秒（射雕第二章约 9~23 秒），开打时浏览器会卡住。修为现在只管天赋点和主线的建议修为，不影响敌人强度。

**决定**：
- 强度 = 三势各自最狠一招的攻击值（武功等级、内功、兵器、天赋、轻功都算进去）+ 气血。
- 不再模拟，直接算一回合的期望交换：敌人按 ai 权重出招（只算它有招的势），玩家以六成的机会出克制它的势（虚招每 1 点 cunning 再扣 0.5%）；按真实的克制倍率（克 ×1.5、被克 ×0.5、守化解巧招的反震）、对方护体、招式附加效果（内伤 +60%、破绽 +30%、点穴让对方少出手一回合）算双方伤害。
- 敌人气血放缩到约 6 回合打完（0.25 ~ 3 倍，D-102 的封顶保留），伤害放缩到打完时玩家约掉六成气血。多个敌人按排列顺序一个个倒下，正在打的按猜对率算，其余同时出手的按瞎猜算。NPC 队友的输出和分担火力按玩家的一半算（常出辅助招，也会先倒下）。
- 计算从几秒降到几毫秒。
- 结果（84 场必胜剧情战 × 开局 / 入门 / 二袋 / 后期）：猜对 60% 时胜率中位数 95~100%，十分位 63~88%；猜对 80% 时中位数 100%，十分位 88~95%。
- 这放宽了 D-051 用户定的"猜对八成才能赢"：用户这次明确说敌人太强。觉得太容易，调 `ADAPT_TAKEN`（打完掉多少气血）或 `ADAPT_ACC` 就行。（刻度是代为决定的）
- 校准时发现的两个坑，写进了公式：敌人 ai 里写了某势但它没有这一势的招时，引擎不会出这一势（黑白子只有巧和守）；敌人主要出巧招时，玩家主要用的是守招，守招往往最弱——所以不能只看玩家最强的那一势。

### D-329 修：playtest 里第九、十章的"通过"是假的（笑傲）

写第十一章时发现：`playtest-xiaoao.mjs` 里 **ch9、ch10 的调用根本没有被写进三条路线**——前几次用 `node -e` 做的字符串替换在 shell 里被引号吃掉，脚本照常打印 "ok"，我就当它成了。于是第九、十章只定义了测试函数、从来没有跑过，输出却是一行漂亮的"✓ 第一~十章全部走通"。

**两个教训**：

1. **改脚本用 Edit，不要用 `node -e` 拼字符串**：shell 把 `'` 和反引号吃掉之后，`String.replace` 找不到锚点也不会报错，只会静默什么都不做。真要用脚本改，**替换函数必须在找不到锚点时 `process.exit(1)`**（本次已改成这样）。
2. **测试的"通过"要能看出覆盖了什么**：现在的结尾那行只说"第一~N 章"，是我自己写死的字符串。往后加章节时，先确认三条路线里真的多了 `chN(...)` 的调用（`grep -c "chN(g, label"` 应当是 3 加 1 个定义）。

实测确认门槛本身是好的：巧类外功 80 级时去第九章的山门，选项只有"眼下绕不上去"——条件判定按 `player.skills` 的真实等级走，没有被 `cap` 蒙混。

### D-340 重新过了一遍笑傲全线的战斗强度（笑傲）

**用户要求**（2026-10-18）：自适应改过之后（D-106、D-107），把笑傲的战斗强度重新过一遍。

**先修了测量工具**。`tools/balance.mjs` 的四档角色（开局／入门／二袋／后期）练的是基础武功和丐帮武功，和"按笑傲剧情一路走下来"的玩家对不上——笑傲的玩家手上是翻天掌、衡山剑法、七弦指，气血靠养心诀撑。用错档位的读数荒腔走板：同一场战斗开局 100%、入门 0%、二袋 18%。
新建 **`tools/balance-xiaoao.mjs`**：按本线进度分五档（初／早／中／晚／末，分别对应第 1-2、3-4、5-8、9-12、13-18 章，武功按"练到上限八成"估），每场战斗只看它该看的那一档，一条命令出全表。

**测量结果**（25 场必胜战，猜对 80%）：

| 该看的那一档 | 落在 60~80% | 偏易（≥90%） | 偏难（<60%） |
|---|---|---|---|
| 初（1-2 章） | 0 | 4 | 0 |
| 早（3-4 章） | 1 | 2 | 1 |
| 中（5-8 章） | 0 | 6 | 0 |
| 晚（9-12 章） | 0 | 4 | 0 |
| 末（13-18 章） | 2 | 3 | 2 |

**关键发现一：在自适应生效的区间里，内容侧改敌人强弱几乎没有效果。**
自适应把敌人气血缩放到"约 6 回合打完"（`ADAPT_ROUNDS / base`），而 `base` 与敌人血量成正比——**敌人血乘以多少，自适应就除以多少，最后打起来是一样的**。实测：把林平之从战斗力 335 降到 299、把终章的岳不群从 441 降到 394，两场的胜率纹丝不动（55%、57%）。所以这两处改动已经改回去了，战力曲线保持原样。

**关键发现二：偏易是全局的，不是笑傲独有。** 拿同一档玩家去打别的主线的后段：射雕「梅超风」100%、天龙「慕容复」98%、天龙「摩云子」100%。根子在 `ADAPT_TAKEN = 0.6`——它的意思是"按自适应算，打完这一场玩家大约掉六成血"，那么猜对 80% 的玩家自然几乎必胜。要让读数回到 D-051 的 65%，得把 `ADAPT_TAKEN` 提到 0.85~0.95（或者调 `ADAPT_ROUNDS`）。**这是引擎参数，按协作规则这边不动**，报告给用户和主线会话。

**关键发现三：内容侧真正还有效的，是把敌人从"撞下限"的区间拉回来。** 自适应的气血系数下限是 0.25、伤害下限 0.1；撞了下限就说明"敌人相对玩家太强，自适应想削也削不动"，这时战斗会退化成"打得完／打不完"的二极管——第十一、十三、十四章原本就是这样（对应档 0%~3%）。
**已做的调整：给第九~十八章的敌人统一降血**（`hpx` 0.45~0.6，群战的小兵降得最多）。降完之后这些战斗的自适应系数从 ×0.25（撞限）回到 ×1.0~×2.3 的正常区间，胜率从 0% 回到 75%~100%——虽然还偏易，但至少**从"不可能赢"变成了"能打"**，而且等引擎参数调定之后，它们会跟着一起回到正常难度。

**结论**：笑傲的战斗力曲线（33 → 441）本身没有问题，和天龙、射雕在同一量级；现在全线偏易是引擎自适应的参数问题。等 `ADAPT_TAKEN` 一类的参数调定，用 `node tools/balance-xiaoao.mjs` 一条命令就能把全线重测一遍。
